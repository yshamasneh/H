# Native configuration ownership

The mobile application intentionally uses a mixed Expo setup:

- **Android is a checked-in, hand-maintained native project.** Files under `android/` are authoritative for the binary. `app.json` remains the shared source for values used by Expo tooling, so critical duplicated values are gated by `npm run check:native-config`.
- **iOS uses Continuous Native Generation.** There is no checked-in `ios/` directory; Expo/EAS generates it from `app.json` and config plugins. If an iOS directory is ever committed, the consistency check deliberately fails until equivalent native assertions are added.

Because Android is maintained rather than regenerated for every build, the Expo Doctor `appConfigFieldsNotSyncedCheck` opt-out is intentional and is retained. Removing it would report expected differences and would not make `app.json` authoritative over the existing Android project.

## Critical synchronization map

| Setting | Expo source | Android authority |
| --- | --- | --- |
| Package/namespace | `android.package` | `app/build.gradle` and Kotlin package path/declarations |
| App/version baseline | `name`, `version`, `android.versionCode` | resources and `app/build.gradle`; EAS production build numbers remain remote/auto-incremented |
| Deep-link schemes | `scheme` | `AndroidManifest.xml` (`jovo` and Expo development-client scheme) |
| Permissions | `android.permissions`, `android.blockedPermissions`, config plugins | `AndroidManifest.xml`; Camera/Internet/Vibrate are plugin/runtime requirements, while audio/storage/overlay remain removed |
| Expo Updates | `updates`, `runtimeVersion`, EAS project ID | `AndroidManifest.xml` metadata |
| Release channel | production profile `channel` | production request header in `AndroidManifest.xml` |
| New architecture | `newArchEnabled` | `gradle.properties` |
| Notification channel | runtime Push setup | `src/core/push-notifications.ts` (`orders`, high importance) |
| Driver delivery-alert channel and sound | `expo-notifications` plugin `sounds` | `src/core/push-channels.ts` (`delivery-alerts`, max importance) and `android/app/src/main/res/raw/jovo_delivery.wav` |

`check:native-config` also protects the native-only release choices that a standard prebuild removes: release minification/resource shrinking, no debug signing for release, and a disabled development-client network inspector.

## Background location during a delivery needs a new native build (0.15.0)

Drivers' location keeps reporting while a delivery is active even when JOVO is in the background (for
example while a navigation app is open). It is native code and permissions, so it ships only in a new
Android and iOS build, and the app version moved to `0.15.0` (build 15) so no earlier binary is ever
sent this JavaScript over the air (the runtime version policy is `appVersion`; `expo-task-manager` is a
new native module and would crash an older binary at startup).

| Setting | Expo source | Android authority |
| --- | --- | --- |
| Background location permissions | `android.permissions` + `expo-location` plugin flags | `AndroidManifest.xml` (`ACCESS_BACKGROUND_LOCATION`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`); the location foreground service itself comes from the `expo-location` library manifest |
| iOS background mode and Always usage strings | `expo-location` plugin (`isIosBackgroundLocationEnabled`, `locationAlways*Permission`) | generated at `eas build` |
| The tracking task | `expo-task-manager` | `src/core/background-location.ts`, imported first in `index.ts` so it exists when the OS starts it with no screen mounted |

`npm run check:native-config` fails if any of these, the task manager dependency, the task definition, or
the in-app disclosure component is missing, because a build with the permission but no disclosure is what
Play Store review rejects. Store-console work (Data safety, the location declaration, the video) is listed
in `docs/play-store-background-location.md`.

**Device checklist** (none of this can be verified without a phone): as a driver, accept a delivery and
read the disclosure; tap Continue and grant "Allow all the time" (Android 11+ opens settings; iOS asks
"Always" a little later); tap Navigate and confirm the map in the admin console keeps moving while the
navigation app is on top; confirm the "JOVO delivery in progress" notification (Android) or blue bar (iOS)
is visible; mark the delivery delivered and confirm both disappear and the admin position stops updating;
cancel a delivery from the admin console while the driver is in another app and confirm tracking stops.

## The delivery-alert sound needs a new native build

The driver's "new delivery" alert plays a custom JOVO sound (`assets/sounds/jovo_delivery.wav`, regenerated by
`node scripts/generate-alert-sound.mjs`). A sound file is part of the binary, so **this cannot ship through an OTA / EAS Update**;
it needs a new Android build and a new iOS build. It is also why the app version moved to `0.14.0` (build 14): the runtime version
policy is `appVersion`, so an update published for `0.14.0` is only ever delivered to binaries that contain the sound. Publishing
this JavaScript to `0.13.0` binaries would create the `delivery-alerts` channel against a sound that is not there, and an Android
channel cannot be corrected once created (only a reinstall or a new channel id fixes it).

- **Android** (hand-maintained project): the sound lives in `res/raw/jovo_delivery.wav`. The name must be lowercase letters, digits
  and underscores, which is why it is not `jovo-delivery.wav`. The channel is created in JS at token registration, for drivers only.
  Sound, channel id and file name are pinned by `npm run check:native-config` and by the API's `push-presentation.test.ts`.
- **iOS** (generated from `app.json`): the `expo-notifications` plugin entry lists the sound, and the plugin bundles it into the app
  on the next `eas build`. The plugin also adds the `aps-environment` push entitlement, which was previously not configured.
  The API names the file in the push payload (`sound: "jovo_delivery.wav"`). iOS plays it on the ringer/silent-switch rules of a
  normal notification; louder behaviour (Critical Alerts, Time Sensitive) needs an Apple entitlement and is not enabled.
- **After the build**, on a real phone: log in as a driver, allow notifications, go online, close the app, and mark a test order
  ready for pickup. Check the sound, the vibration, the heads-up banner, and that tapping opens the driver's home.

## Safe update workflow

1. Change `app.json` and the maintained Android files together when a mapped value changes.
2. Run `npm run check:native-config --workspace @wasel/mobile` and Expo Doctor.
3. To compare current CNG output, copy the Mobile project to a temporary directory and run `expo prebuild --platform android --no-install --clean` there. Do not run a clean prebuild over the maintained project merely for comparison.
4. If Android is intentionally regenerated, review the entire native diff, run `python scripts/post-prebuild.py`, rerun the consistency check, and verify an unsigned Android build. Never accept the template's release debug signing.

The production channel is the checked-in Android default. Preview/development native builds must use the corresponding channel during their build process; do not manually ship the production manifest as a preview binary without confirming the embedded update request header.
